# CRM: учёт звонков и встреч

REST API для отдела, который обзванивает организации и назначает встречи. Сделано на Python, FastAPI и SQLite. ORM нет, все запросы к базе написаны обычным SQL, чтобы было видно, что именно проверяется.

## Запуск

### Вариант 1. Docker

Нужен Docker с compose.

```bash
git clone <ссылка на репозиторий> crm-calls-api
cd crm-calls-api
docker compose up --build
```

API будет на http://localhost:8000, документация Swagger на http://localhost:8000/docs. База лежит в docker volume `crm-data`. Чтобы начать с чистой базы, выполните `docker compose down -v`.

Тесты внутри контейнера, когда он запущен:

```bash
docker compose exec api pytest -q
```

### Вариант 2. Без Docker

Нужен Python 3.10 или новее (проверял на 3.12).

```bash
git clone <ссылка на репозиторий> crm-calls-api
cd crm-calls-api
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --port 8000
```

Тесты:

```bash
pytest -q
```

### Переменные окружения

Есть одна переменная, `DB_PATH`, это путь к файлу SQLite. По умолчанию это `crm.db` в текущей папке, в Docker это `/data/crm.db`. Таблицы создаются сами при старте приложения из `migrations/*.sql`, отдельно запускать миграции не нужно. Применённые файлы записываются в таблицу `schema_migrations`, поэтому повторный старт ничего не ломает.

### Примеры запросов

В `examples.sh` лежат curl-запросы на все эндпоинты и на каждый вид отказа. Их нужно запускать на пустой базе при уже работающем API:

```bash
bash examples.sh
# если API на другом адресе:
API=http://localhost:8001 bash examples.sh
```

## Эндпоинты

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/companies` | добавить организацию: `name`, `bin` (12 цифр), `phone` |
| GET | `/companies?status=&limit=20&offset=0` | список с фильтром по статусу и пагинацией, в ответе есть `total` |
| POST | `/calls` | результат звонка: `no_answer`, `refused`, `meeting_set` |
| POST | `/meetings` | назначить встречу: `company_id`, `manager_id`, `start_at` |
| PATCH | `/meetings/{id}` | перенести `{"start_at": "..."}` или отменить `{"status": "cancelled"}` |
| GET | `/meetings/{id}` | встреча с историей изменений (добавил сам, чтобы было видно историю) |
| GET | `/managers/{id}/schedule?date=2030-01-07` | расписание менеджера на день |
| POST | `/managers` | добавить менеджера (в ТЗ нет, но без него некому назначать встречи) |

Время в API принимается и отдаётся в UTC в формате ISO 8601, например `2030-01-07T05:00:00Z`. Время с другим смещением тоже принимается (`2030-01-07T10:00:00+05:00`) и переводится в UTC. Время без часового пояса отклоняется с 422, потому что непонятно, в какой зоне оно указано.

Все ошибки приходят в одном формате:

```json
{"error": {"code": "manager_busy", "message": "У менеджера уже есть встреча #1 в 2030-01-07T05:00:00Z, время пересекается"}}
```

| Код HTTP | Когда |
|---|---|
| 404 | организация, менеджер или встреча не найдены |
| 409 | конфликт с уже существующими данными: менеджер занят, у организации уже есть встреча, БИН уже есть, встреча отменена или прошла |
| 422 | запрос сам по себе неправильный: нерабочее время, прошлое, неверный БИН, `meeting_set` без встречи |

## Бизнес-правила и как они сделаны

Все проверки встреч находятся в одной функции `check_slot` в `app/main.py`, а расчёт рабочего времени лежит в `app/rules.py`.

1. **Встреча длится 60 минут.** Конец встречи сервер считает сам, клиент передаёт только начало.
2. **Рабочие часы: пн–пт, 09:00–18:00 по Asia/Almaty.** Начало переводится в Алматы, и проверяется, что начало не раньше 09:00, а конец не позже 18:00. Начало в 17:00 проходит, начало в 17:01 и в 17:30 нет. Выходной определяется по дню недели в Алматы, а не в UTC. Казахстан с марта 2024 года живёт по UTC+5, и смещение берётся из базы часовых поясов, а не захардкожено. Отдельный тест проверяет, что смещение действительно +5.
3. **Встречи одного менеджера не пересекаются.** Интервалы полуоткрытые `[начало, конец)`: встречи пересекаются, если `A.начало < B.конец и B.начало < A.конец`. Поэтому 10:00–11:00 и 11:00–12:00 не конфликт. Отменённые встречи не учитываются.
4. **У организации одна активная встреча.** Подробнее в разделе про трактовки ниже.
5. **`meeting_set` требует встречу.** Сначала создаётся встреча через `POST /meetings`, потом звонок с `meeting_id`. Встреча должна существовать, принадлежать той же организации и не быть отменённой, иначе 422. Передавать `meeting_id` с другими результатами тоже нельзя.
6. **История переносов.** У встречи есть поле `original_start_at`, это время, на которое её назначили в первый раз, и оно не меняется. Кроме того, каждое действие (создание, перенос, отмена) пишется отдельной строкой в таблицу `meeting_history` со временем действия. `GET /meetings/{id}` отдаёт встречу вместе с историей.
7. **Никаких 500 на отказах.** У каждого отказа свой код и сообщение на русском. Ошибки валидации FastAPI переделаны в тот же формат.

Дополнительно я решил, что встречу нельзя назначить или перенести на прошедшее время, и прошедшую или отменённую встречу нельзя менять.

## Трактовки неоднозначных мест

- **«Две активные встречи одновременно» у организации.** Я понял это так: у организации может быть только одна активная встреча, то есть не отменённая и ещё не закончившаяся, независимо от времени и менеджера. Можно было понять и как «встречи организации не пересекаются по времени», но тогда правило почти повторяет правило 3, а по смыслу отделу не нужно, чтобы два оператора договорились с одной компанией на два разных дня. Если нужна вторая трактовка, меняется один SQL-запрос в `check_slot`.
- **Порядок «звонок и встреча».** Встреча создаётся первой, звонок ссылается на неё. Создавать встречу внутри `POST /calls` я не стал, чтобы не дублировать логику.
- **Статус организации** для фильтра `GET /companies?status=` равен результату последнего звонка, а до первого звонка он `new`.
- **Менеджеры.** Эндпоинта в ТЗ нет, поэтому миграция создаёт двух менеджеров (id 1 и 2), и есть `POST /managers`.
- **Пагинация** сделана через `limit` и `offset`: по умолчанию 20 записей, максимум 100.
- **Расписание на день** считается по дню в Алматы, с 00:00 до 24:00 местного времени. В ответе только активные встречи, отменённые не показываются.

## Тесты

Всего 31 тест, они проходят за меньше чем секунду, каждый тест работает на своей чистой базе.

- `tests/test_rules.py` проверяет границу рабочего дня (08:59, 09:00, 17:00, 17:01, 17:30, 18:00), выходные, перевод UTC в Алматы (включая воскресенье 23:00 UTC, которое уже понедельник 04:00 в Алматы) и смещение +5.
- `tests/test_meetings.py` проверяет пересечения у менеджера (наложение с обеих сторон и стык с обеих сторон), то же время у другого менеджера, 17:30 и 17:00 через API, время без пояса, прошлое, правило организации, освобождение слота после отмены, историю переносов, неудачный перенос, который ничего не меняет, перенос, пересекающийся сам с собой, 404 и расписание по дню Алматы.
- Там же тест на гонку: 10 потоков одновременно бронируют один слот, должен пройти ровно один. Я проверил, что тест действительно ловит проблему: если убрать блокировку в `app/db.py`, он падает в 16 запусках из 20, а с блокировкой падает в 0 из 20.
- `tests/test_companies_and_calls.py` проверяет валидацию БИН, дубль БИН, фильтр с пагинацией, `meeting_set` без встречи, с несуществующей встречей и со встречей чужой организации.

## Что сделано и что нет

Сделано всё из обязательной части: шесть эндпоинтов из ТЗ, семь бизнес-правил, схема в SQL-миграции, тесты, запуск через Docker и без него, примеры запросов.

Чего нет:
- Нет справочника праздников. Встреча 1 января или 22 марта в будний день пройдёт.
- Нет отметки «встреча состоялась». Активная встреча просто перестаёт быть активной, когда её время прошло.
- Нет списка звонков по организации (`GET /calls`), в ТЗ его не было.
- SQLite выбран ради простоты запуска. Для нескольких экземпляров сервиса нужен Postgres, что в этом случае поменяется, описано в REFLECTION.md.
